# 智能路由 OmniRoute 方案对齐实施报告

日期：2026-07-28

## 范围

本轮只参考 OmniRoute `release/v3.8.49` 中智能路由的请求复杂度、候选评分、健康隔离、重置窗口和会话稳定性思路，并复用本项目已有能力实现。没有引入 OmniRoute 的外部配置体系、外部路由服务或部署方案，也没有改变 `ContextConsensus` 的安全边界。

## 已完成

### 请求复杂度与任务匹配

- 保留任务复杂度与上下文需求分离的既有原则。
- 任务复杂度补充有限工具数量、代码/迁移、数学/证明和根因分析信号，避免工具数量无限放大分数。
- 新增 `general`、`translation`、`coding`、`reasoning`、`analysis`、`creative` 任务类型。
- 根据复杂度、任务类型和工具/Schema 要求生成推荐质量层级，并作为 `task_match` 因子参与评分。

### 评分维度与数据有效性

候选评分新增：

- `task_match`：任务类型、模型专项画像和推荐质量层级的匹配度。
- `context`：请求所需 token 与候选上下文窗口余量，已有上下文画像只作为小比例补充。
- `cache`：已有渠道亲和规则命中 `prompt_cache_key` 等缓存键时的缓存亲和。
- `reset_window`：运行时故障隔离窗口的恢复进度。
- `affinity`：非缓存键的会话亲和。

同时修正基础评分数据：

- `reliability` 不再固定为 `1`，改为读取按“渠道 + 模型”维护的运行时成功 EWMA，并结合多 Key 渠道可用 Key 比例。
- 渠道 `Weight` 不再冒充吞吐量；没有真实吞吐数据时使用中性分 `0.5`，不参与候选间差异制造。
- 渠道表中的 `ResponseTime` 只来自手工或定时测试，不再直接作为智能路由延迟分。没有真实请求样本时使用中性分 `0.5`；同一“渠道 + 模型”至少积累 3 次有效真实请求延迟后，延迟 EWMA 才参与 `latency` 评分。
- 延迟样本按每次实际上游尝试独立计时，重试不会复用请求级开始时间或前一次尝试的首包时间。流式请求使用“尝试开始到上游响应体首次读到非空数据”的 TTFT；SDK 事件流和 WebSocket 使用既有首事件/首消息标记。非流式请求和异步任务提交使用单次上游尝试的完整耗时。
- 流式请求成功但没有观测到有效首包时，只记录健康成功，不写入延迟 EWMA，避免退回整段流式生成耗时污染评分。
- HTTP 响应体的原始首包只写入当前上游尝试；请求级 `FirstResponseTime` 仍由有效流事件、SDK 事件或 WebSocket 消息确认。失败尝试读取 429/5xx 错误正文时不会抢先污染最终成功请求的 TTFT、消费日志和性能指标。

### 健康状态、故障隔离与重置窗口

新增进程内运行时健康跟踪器，按“渠道 ID + 模型名”隔离：

- 状态为 `healthy`、`degraded`、`open`、`half_open`。
- 只把渠道错误、现有自动禁用错误和现有可重试状态码记录为健康失败，普通客户端 `400` 保持中性。
- 连续 3 次失败进入 `open`，初始冷却 5 秒；半开探测失败后指数增加，最大 5 分钟。
- 冷却到期进入 `half_open`；成功请求清除连续失败和隔离窗口，并继续用 EWMA 恢复可靠性。
- 半开状态使用 5 秒单探针租约；租约只在每次即将真实调用上游前获取，本地正文校验、计费等前置失败不会占用。重试也必须逐次重新检查，避免旧候选绕过最新健康状态。
- `open` 候选始终硬隔离，全部候选均为 `open` 时返回无可用候选，不绕过故障隔离。
- 多 Key 渠道会检查可用 Key 比例；全部 Key 不可用时标记为硬不可用并始终拒绝，部分不可用时按 `degraded` 处理。
- 健康条目 15 分钟无观测后自动清理；未带真实延迟的普通成功不会创建新条目，限制进程内状态增长。

运行时健康画像仅作为智能路由软状态，项目已有渠道禁用、自动禁用和被动恢复仍是全局硬状态。

### 上下文/缓存亲和与会话稳定性

- 复用现有渠道亲和 HybridCache、TTL、Redis/内存回退和成功后切换逻辑，不新建第二套会话缓存。
- 缓存键来源命中记为 `cache`，其他亲和键来源记为 `session`，分别进入评分日志。
- 评分先确定真实模型；若该模型存在健康、综合分差不超过 `0.1` 的亲和渠道，则在同模型渠道序列内优先该渠道。降级渠道或分差过大的渠道不会因亲和被强制提升，避免会话稳定性覆盖健康与质量底线。
- 最终成功渠道继续写回现有亲和缓存，重试仍只消费本次选定真实模型的渠道序列。

## 审计字段

`other.smart_routing` 新增或补充：

- `task_type`
- `recommended_tier`
- `selected_health`
- `score_factors.task_match`
- `score_factors.context`
- `score_factors.cache`
- `score_factors.reset_window`

日志只记录枚举、数值和渠道 ID，不记录请求正文、缓存原值、API Key、Token 或 Secret。

## 限制

- 运行时健康画像当前为单进程状态，多实例之间可能暂时不同；数据库渠道状态和渠道缓存仍负责全局硬隔离。
- `reset_window` 当前表示本地健康熔断冷却，不表示供应商账户配额重置时间；后者需要可靠的上游配额元数据，本轮按范围不引入外部配置。
- 没有真实吞吐指标时保持中性分。后续若增加渠道级可验证吞吐采样，应替换中性值，而不是重新复用渠道权重。
- 流式 TTFT 当前定义为首个上游响应数据，不保证等同于首个可见文本 token；若供应商先发送心跳或协议控制数据，该数据也会成为首包。后续若需要模型生成速度比较，应另行采集首个有效内容时间和输出 token 吞吐量，不能混入当前延迟指标。

## 验证

已覆盖以下回归：

- 复杂度、任务类型和推荐层级。
- 任务匹配、上下文、缓存、会话亲和和重置窗口评分。
- 健康状态转换、指数冷却、半开恢复、并发安全和渠道/模型隔离。
- 半开单探针门禁、健康状态 TTL 清理和真实请求延迟 EWMA。
- 重试之间的逐尝试计时隔离、流式首包 TTFT、非流式完整尝试耗时，以及无首包流式成功不产生延迟样本。
- HTTP 流式响应体只在首次读取到非空数据时标记首包，空读取和 EOF 不产生首包记录。
- 首次失败尝试的错误正文只标记该尝试，第二次流式成功后请求级首包时间指向成功流；请求级首包时间统一通过并发安全快照读取。
- 讯飞流式 WebSocket 和火山 TTS WebSocket 在首个有效响应/音频负载到达时记录首包。
- 多 Key 可用比例和运行时可靠性合并。
- 始终隔离 `open`，并始终拒绝全部 Key 不可用的渠道。
- 会话稳定性只在已选真实模型内部、健康且分差有界时优先亲和渠道。
- 运行时失败只采纳渠道级或可重试错误。

```bash
go test -race ./relay/common ./relay/channel ./controller ./service/smartrouting -run 'Test(UpstreamAttempt|RelayInfoRequestFirstResponse|FirstResponseReadCloser|RecordRuntimeHealthSuccessForAttempt|GetChannel|ShouldRecordRuntimeHealthFailure|RuntimeHealth)' -count=1
```
